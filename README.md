# Project Reflex

**Experimental diffusion-model runtime for tool routing and conditional generation.** Built by Tawananyasha Mukoriwo on an NVIDIA DGX Spark. This is a research prototype; see [RESULTS.md](RESULTS.md) for full evidence and limitations.

## How it works

Reflex serves Google's DiffusionGemma 26B-A4B-it through `/v1/chat/completions`. Tool routing and argument synthesis go through the model's **own trained function-calling format** (a native `<|tool_call>call:name{args}<tool_call|>` protocol built into its chat template) driven by the **official** `model.generate()` block-diffusion sampler -- not a custom canvas or hand-written extractor.

DiffusionGemma generates in fixed 256-token blocks. Reflex now observes the official sampler's argmax draft after every decoder forward. When a draft contains exactly one complete, parseable call to an offered argument-free tool, the server returns that call immediately. Calls with parameters, incomplete drafts, unknown tools, and direct responses continue through the official sampler. This is a real System-1/System-2 transition inside one model invocation: simple actions can stop after one decoder step, while harder outputs retain the model's native generation path.

This optimization reduces denoising steps, not canvas width. An earlier attempt to reduce `max_new_tokens` below 256 did not reduce the checkpoint's fixed block allocation, so that claim remains retired. `reflex_metadata.steps_executed` now reports the actual decoder-forward count; a telemetry bug that divided by the padded 256-slot width instead of the non-pad generated-token count was fixed on 2026-09-23.

This replaces an earlier architecture (see [RESULTS.md](RESULTS.md) and `NOTES.md`) that asked the model to select a tool by classifying an index into unused-vocabulary control tokens on a 4-token canvas, with argument values either extracted by deterministic regex or generated by a hand-rolled whole-canvas-argmax loop. That scheme reached decent tool-name accuracy after LoRA fine-tuning but never produced working free-text arguments (0/5 measured) and only handled a single explicit numeric literal via regex, not learned synthesis. Root-cause investigation found the model already has a real, trained tool-calling mechanism that the custom scheme was bypassing entirely; switching to it, zero-shot, with no training, outperformed the fine-tuned custom scheme on a set 26x larger. The old scheme's code remains inspectable in git history; it is no longer the serving path.

| Path | Current implementation | What still needs proof |
| --- | --- | --- |
| Atomic (no args) | Exit on the first complete native draft; fail closed unless the selected name is an offered zero-argument schema | Calibration on a larger atomic set and a same-run full-generation A/B. |
| Primitive args (numeric/enum/bool) | Continue the official sampler, parse native arguments, then validate against the selected schema | Official BFCL AST scoring instead of the current loose containment check. |
| Free-text / nested-object args | Continue the same sampler with the full block and fail-closed schema validation | The model sometimes answers directly or emits invalid required fields; frequency and mitigation remain open. |

## Evidence status

On a frozen, **1,051-example independent held-out routing set** (sourced from BFCL's `live_multiple` category -- a source file disjoint from the one used for any training data in this repo, with exact query-overlap checked and excluded), the native tool-calling path reached **93.3% tool-name accuracy** and **~77% fully-correct calls** (right tool and valid arguments, including free-text and nested-object arguments), using the **base model with zero training**. Accuracy was **93.1%/77.3%** under a deterministic per-item candidate-order permutation -- i.e. no positional shortcut -- and flat across menus of 2 to 10 candidates. This is a materially larger and more rigorous result than an earlier 40-example (38 after de-duplication) probe of the old, custom, LoRA-fine-tuned scheme.

A live smoke test of the actual serving code (not just the evaluation script) confirmed both of the old scheme's headline failures are fixed: `set_volume(level=57)` now returns the exact value (the old scheme emitted `level: 1`), and the prompt that previously scored 0/5 on free-text ("write an email to Alice apologizing for the delay") now produces a complete, coherent email.

A held-out atomic evaluation on 2026-09-23 returned the correct tool on **25/25** BFCL-derived cases. **24/25** exited after one decoder step; the remaining item declared optional parameters and correctly used the argument-capable path in two steps. Warm mean/p50 latency was **697/707 ms**, compared with **978/1,006 ms** for the earlier full-generation atomic subset (a historical, non-interleaved comparison): about **29% lower latency** or **1.40x throughput-equivalent speedup**, with unchanged 25/25 accuracy. The raw trace is `experiments/atomic_early_exit_20260923T070911Z.jsonl`.

A deterministic 52+52 held-out probe measured increasing work with output complexity. Atomic-bucket calls used **1.04 mean steps / 697 ms**; primitive calls used **2.96 / 1,490 ms** (50/52 tool names, 40/52 loose full arguments); free-text/nested calls used **3.65 / 1,627 ms** (45/52 names, 33/52 loose full arguments). None of the 104 non-atomic requests exited through the atomic gate. The full 1,051-item evaluation remains the main quality result.

**Not yet resolved:** per-call latency for anything beyond atomic calls is ~1.0-2.6s (real generation, not a single masked-token read) because the model performs an internal reasoning step before deciding on a tool call -- no KV-cache reuse is implemented yet, which is the clearest next latency win. The atomic exit is a syntactic/schema gate and has no calibrated correctness probability (the previous conformal-risk-gate work does not apply to it and is explicitly deferred, not deleted -- see [RESULTS.md](RESULTS.md)). The "loose" argument-match figures above are a conservative containment check, not the official BFCL scorer. [RESULTS.md](RESULTS.md) has the full breakdown, historical v1/v2 numbers, and a verdict section.

## Run locally

A CUDA-capable machine with a substantial memory budget is required for the BF16 checkpoint.

~~~bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# Set DIFFUSION_GEMMA_PATH in .env. Leave REFLEX_LORA_PATH pointing at a
# nonexistent path (the default) to run the validated native tool-calling
# path on the base model -- see .env.example and src/engine/runner.py.
python -m src.server
~~~

The server defaults to port 8090 and exposes `/health`, `/v1/models`, and `/v1/chat/completions`. Example request:

~~~bash
curl http://127.0.0.1:8090/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"reflex-diffusiongemma","messages":[{"role":"user","content":"Set volume to 57"}],"tools":[{"type":"function","function":{"name":"set_volume","description":"Set system volume level","parameters":{"type":"object","properties":{"level":{"type":"integer","minimum":0,"maximum":100}},"required":["level"]}}}]}'
~~~

Responses include `reflex_metadata` with execution path, tier, engine time, and decoder forward-pass count (counted directly for early exits and recovered from the official generator's non-pad `tokens_per_forward` statistic otherwise). `confidence` is **not** a calibrated probability; atomic early exits currently report `0.0` rather than inventing one. Check the tool name and arguments directly, since HTTP 200 does not imply a correct action.

## Reproduce and evaluate

- `python scripts/prepare_bfcl_live_eval.py` rebuilds the 1,051-example independent routing set from BFCL `live_multiple`, with provenance and overlap-checking against `data/bfcl/{train,cal,test}.jsonl`.
- `python experiments/eval_native_tool_calling.py --skip-lora` reruns the full routing + argument-accuracy evaluation (both candidate-order conditions) against the base model.
- `python experiments/eval_atomic_early_exit.py` evaluates every held-out atomic example against a running server; `python experiments/eval_tiered_adaptive_compute.py` records steps, latency, and correctness across primitive and free-text samples.
- `python scripts/prepare_datasets.py --verify-splits` checks split overlap for the historical v1/v2 datasets. The BFCL data here remains a **single-call routing subset**, not the official full BFCL score.
- `python -m unittest discover tests/` runs fast code-level tests (35 passing, including 13 for the native tool-call parser/validator in `src/engine/native_tool_calling.py`). GPU integration scripts under `tests/` (`test_fast_path_reflex.py` and siblings) are standalone and still assert some behavior of the retired custom scheme; treat them as needing an update pass before trusting their output.

For a paper, the project still needs the official BFCL AST scorer in place of the loose argument-match check used here, a matched AR baseline evaluated on the same 1,051-item set, KV-cache reuse for the native path, a larger calibration set and confidence/accuracy curve before any risk-bound claim, and measurement of how often the model bypasses an offered tool in favor of a direct response. The [Google model guide](https://developers.googleblog.com/diffusiongemma-the-developer-guide/) and [official generation documentation](https://huggingface.co/docs/transformers/en/model_doc/diffusion_gemma) describe the base model and its native tool-calling chat template. A [vLLM structured-read prototype](https://github.com/vllm-project/vllm/pull/57250) demonstrates short seeded canvases and one-step categorical decisions; this project instead reads the model's native intermediate tool-call drafts and terminates verified zero-argument actions early, while retaining the official sampler for harder outputs and novelty must still be stated modestly and supported by comparisons.
