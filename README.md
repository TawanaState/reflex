# Project Reflex

**Experimental diffusion-model runtime for tool routing and conditional generation.** Built by Tawananyasha Mukoriwo on an NVIDIA DGX Spark. This is a research prototype; see [RESULTS.md](RESULTS.md) for full evidence and limitations.

## How it works

Reflex serves Google's DiffusionGemma 26B-A4B-it through `/v1/chat/completions`. Tool routing and argument synthesis go through the model's **own trained function-calling format** (a native `<|tool_call>call:name{args}<tool_call|>` protocol built into its chat template) driven by the **official** `model.generate()` block-diffusion sampler -- not a custom canvas or hand-written extractor.

DiffusionGemma generates in fixed `canvas_length`-token blocks (256 for this checkpoint): an earlier version of this server tried to shrink `max_new_tokens` per tool-schema complexity to save compute (e.g. 48 tokens for an argument-free tool menu), but a live measurement showed this had **no effect** -- a request still comes back with a full 256-token block's worth of `completion_tokens` regardless, because block generation is not exactly truncated to an arbitrary sub-block length. That budget-scaling has been removed rather than left in as an unverified optimization. The real adaptive-compute signal in this architecture is the official sampler's own entropy-based early stopping of *denoising steps within a block* (`reflex_metadata.steps_executed`, recovered from the generator's own `tokens_per_forward` output) -- that genuinely varies with request difficulty (observed 26-39 forward passes across a handful of live calls, well under the configured 48-step ceiling) and isn't something this server controls or fabricates.

This replaces an earlier architecture (see [RESULTS.md](RESULTS.md) and `NOTES.md`) that asked the model to select a tool by classifying an index into unused-vocabulary control tokens on a 4-token canvas, with argument values either extracted by deterministic regex or generated by a hand-rolled whole-canvas-argmax loop. That scheme reached decent tool-name accuracy after LoRA fine-tuning but never produced working free-text arguments (0/5 measured) and only handled a single explicit numeric literal via regex, not learned synthesis. Root-cause investigation found the model already has a real, trained tool-calling mechanism that the custom scheme was bypassing entirely; switching to it, zero-shot, with no training, outperformed the fine-tuned custom scheme on a set 26x larger. The old scheme's code remains inspectable in git history; it is no longer the serving path.

| Path | Current implementation | What still needs proof |
| --- | --- | --- |
| Atomic (no args) | One `generate()` call over one 256-token block | Latency floor with KV-cache reuse (not yet implemented). |
| Primitive args (numeric/enum/bool) | Real generation via the native tool-call format, fail-closed schema validation on the parsed result | Tighter accuracy scoring against the official BFCL AST scorer instead of the current loose containment check. |
| Free-text / nested-object args | Same mechanism, same block size | The model sometimes answers directly instead of invoking an offered tool even when one matches (observed in a live smoke test); frequency and mitigation are open. |

## Evidence status

On a frozen, **1,051-example independent held-out routing set** (sourced from BFCL's `live_multiple` category -- a source file disjoint from the one used for any training data in this repo, with exact query-overlap checked and excluded), the native tool-calling path reached **93.3% tool-name accuracy** and **~77% fully-correct calls** (right tool and valid arguments, including free-text and nested-object arguments), using the **base model with zero training**. Accuracy was **93.1%/77.3%** under a deterministic per-item candidate-order permutation -- i.e. no positional shortcut -- and flat across menus of 2 to 10 candidates. This is a materially larger and more rigorous result than an earlier 40-example (38 after de-duplication) probe of the old, custom, LoRA-fine-tuned scheme.

A live smoke test of the actual serving code (not just the evaluation script) confirmed both of the old scheme's headline failures are fixed: `set_volume(level=57)` now returns the exact value (the old scheme emitted `level: 1`), and the prompt that previously scored 0/5 on free-text ("write an email to Alice apologizing for the delay") now produces a complete, coherent email.

**Not yet resolved:** per-call latency for anything beyond atomic calls is ~1.0-2.6s (real generation, not a single masked-token read) because the model performs an internal reasoning step before deciding on a tool call -- no KV-cache reuse is implemented yet, which is the clearest next latency win. There is no calibrated confidence/exit signal for this path (the previous conformal-risk-gate work does not apply to it and is explicitly deferred, not deleted -- see [RESULTS.md](RESULTS.md)). The "loose" argument-match figures above are a conservative containment check, not the official BFCL scorer. [RESULTS.md](RESULTS.md) has the full breakdown, historical v1/v2 numbers, and a verdict section.

## Run locally

A CUDA-capable machine with a substantial memory budget is required for the BF16 checkpoint.

~~~bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# Set DIFFUSION_GEMMA_PATH in .env. Leave REFLEX_LORA_PATH pointing at a
# nonexistent path (the default) to run the validated native tool-calling
# path on the base model -- see .env.example and src/engine/runner.py.
python -m src.server
~~~

The server defaults to port 8090 and exposes `/health`, `/v1/models`, and `/v1/chat/completions`. Example request:

~~~bash
curl http://127.0.0.1:8090/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"reflex-diffusiongemma","messages":[{"role":"user","content":"Set volume to 57"}],"tools":[{"type":"function","function":{"name":"set_volume","description":"Set system volume level","parameters":{"type":"object","properties":{"level":{"type":"integer","minimum":0,"maximum":100}},"required":["level"]}}}]}'
~~~

Responses include `reflex_metadata` with execution path, tier, engine time, and an approximate decoder forward-pass count (recovered from the official generator's own `tokens_per_forward` output, not a fabricated step count). `confidence` in this metadata is a coarse post-hoc outcome indicator (valid call / invalid args / no call), **not** a calibrated probability -- check the actual tool name and arguments; HTTP 200 does not imply a correct action.

## Reproduce and evaluate

- `python scripts/prepare_bfcl_live_eval.py` rebuilds the 1,051-example independent routing set from BFCL `live_multiple`, with provenance and overlap-checking against `data/bfcl/{train,cal,test}.jsonl`.
- `python experiments/eval_native_tool_calling.py --skip-lora` reruns the full routing + argument-accuracy evaluation (both candidate-order conditions) against the base model.
- `python scripts/prepare_datasets.py --verify-splits` checks split overlap for the historical v1/v2 datasets. The BFCL data here remains a **single-call routing subset**, not the official full BFCL score.
- `python -m unittest discover tests/` runs fast code-level tests (31 passing, including 13 for the native tool-call parser/validator in `src/engine/native_tool_calling.py`). GPU integration scripts under `tests/` (`test_fast_path_reflex.py` and siblings) are standalone and still assert some behavior of the retired custom scheme; treat them as needing an update pass before trusting their output.

For a paper, the project still needs the official BFCL AST scorer in place of the loose argument-match check used here, a matched AR baseline evaluated on the same 1,051-item set, KV-cache reuse for the native path, a genuine confidence/accuracy curve before any calibrated exit claim, and measurement of how often the model bypasses an offered tool in favor of a direct response. The [Google model guide](https://developers.googleblog.com/diffusiongemma-the-developer-guide/) and [official generation documentation](https://huggingface.co/docs/transformers/en/model_doc/diffusion_gemma) describe the base model and its native tool-calling chat template. A [vLLM structured-read prototype](https://github.com/vllm-project/vllm/pull/57250) demonstrates short seeded canvases and one-step categorical decisions; this project's current contribution is different in kind (using the model's trained generative tool-calling capability directly, with the official sampler's own entropy-based per-request step count as the adaptive-compute signal) and novelty must still be stated modestly and supported by comparisons.
