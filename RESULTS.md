# Project Reflex: results and evidence status

**Updated 2026-09-22 (repair sprint, native tool-calling).** This document separates measured observations from claims the current artifacts cannot support. It now has three evidence layers, oldest first: the **v1** adapter (flawed supervision, archived), the **v2** adapter (corrected supervision, custom index-selection scheme, superseded as the serving path but kept for comparison), and **native tool calling** (2026-09-22, the current serving path). Read the final section first if you only want the current status.

## Final verdict (2026-09-22): Tier 2 and Tier 3 can work

Earlier in this repair sprint, Tier 2 argument synthesis was a deterministic regex extractor (not learned), and Tier 3 free-text arguments were 0/5. A senior review of that state recommended one decisive experiment before deciding whether to keep pursuing full tool-calling: a large (500+), genuinely independent, order-randomized routing test, plus replacing the hand-rolled generation loop with DiffusionGemma's *official* sampler.

Running that experiment surfaced the actual root cause: the installed checkpoint's own chat template (`chat_template.jinja`) already implements a trained, native function-calling protocol (`<|tool_call>call:name{key:<|"|>value<|"|>,...}<tool_call|>`, driven by a standard `tools=` argument to `apply_chat_template`), completely independent of Reflex's custom "select a tool index into `<unusedN>`" micro-canvas. The whole Tier 1/2/3 architecture had been asking the model to do a task (index classification into unused-vocabulary slots) it was never instruction-tuned for, instead of the task it was tuned for. That misalignment, not a capability ceiling, is the most likely explanation for the old Tier 2/3 failures.

Using the native format with the *official* `model.generate()` (no custom canvas, no manual argmax loop, no LoRA) on a frozen, **1,051-example independent held-out routing set** (§ "Native tool-calling evidence" below) reached **93.3% tool-name accuracy** and **~77% fully-correct calls** (right tool AND valid arguments, including free-text and nested-object arguments), stable under randomized candidate order. `src/engine/runner.py` has been rewritten to use this mechanism as the live serving path; a smoke test of the rewritten engine against the real model confirmed both previously-broken cases now work: `set_volume(level=57)` (exact, was `level=1` under the old scheme) and a full coherent apology email for the exact prompt that scored 0/5 before.

**What this does not resolve:** latency for anything beyond atomic calls is now ~1-2.6s (real generation with an internal reasoning phase), not the originally proposed sub-150ms single-step read; there is no calibrated confidence signal for the native path (conformal calibration is explicitly deferred, see below); the "loose" argument-match scoring below is a conservative containment check, not the official BFCL AST scorer; and the model sometimes answers directly instead of invoking an offered tool even when a tool call would be the "textbook" response (see the free-text email case below). These are documented, not glossed over.

## Why the previous Pareto chart is not empirical evidence

The old `experiments/benchmark_pareto_suite.py` inserts fixed diffusion accuracy, a two-model cascade point, and an expanded-path accuracy. Its expanded latency adds one 64-token decoder pass to prefill and Step 1; it does not execute a complete 12-20-step generation. `experiments/generate_real_pareto_analysis.py` also samples latency values. Figures derived from these sources are **illustrative historical artifacts**. They should not appear in a paper as a measured accuracy/latency frontier. Both scripts' `main()` now stop immediately with an explicit error; they are retained only as inspectable historical source.

## Supervision correction and version boundary (v1 -> v2)

The original BoolQ data used candidate IDs 2374 and 9484, which decode to unrelated tokens in the installed tokenizer. Correct `no` and `yes` IDs are 1904 and 4443. The original BFCL records assigned every target to option zero; the pinned official answer file places 127 of 200 targets at other positions. `scripts/prepare_datasets.py --repair-existing-supervision` corrected the committed records without changing split membership. `data/supervision_provenance.json` records the source answer URL and hash. **The v1 adapter and all v1 result artifacts predate this correction and are not corrected by editing the data files.**

## Corrected v2: measured local API results (custom index-selection scheme, superseded)

The v2 LoRA was trained on repaired BoolQ and BFCL labels with chat-wrapped prompts, targeting the custom index-selection micro-canvas described above -- **not** the native tool-calling format now used for serving. It is kept on disk (`models/reflex_lora_v2/`) as an archived, documented artifact and is **not auto-attached** by the current server (see `src/engine/runner.py` module docstring and `.env.example`): it has never been evaluated against native tool calling, and attaching an unvalidated adapter to a different serving mechanism could silently change output quality in untested ways.

The deployed exit threshold for this scheme was an **uncalibrated 0.90 heuristic**; it is no longer used, since the native path has no equivalent single-slot softmax confidence to threshold.

## Calibration status: explicitly deferred, not solved

The v1 risk-policy calibration exited on 0/100 test items ("0% error on exits" was vacuous). The v2 scheme's deployed gate was an uncalibrated 0.90 heuristic. Neither `ConformalRiskGate` (`src/risk_gate.py`) nor `DynamicStepScheduler` (`src/engine/scheduler.py`) are wired into the native tool-calling serving path -- both were built around the retired per-slot softmax micro-canvas, which no longer exists. Per external review, this is being treated as explicitly deferred future work rather than something to paper over with a new ad hoc threshold: a real confidence-vs-accuracy curve for the native path (e.g. binned by the model's own `tokens_per_forward` / reasoning-length behavior) would need to be built from a fresh calibration set before any exit policy could be described as calibrated. Both modules remain in the tree with their own passing unit tests for that future work.

## Reproducible next evaluation

1. Preserve v1 and v2 weights as historical/archived evidence (done -- neither is deleted, neither is auto-attached).
2. Run `python -m unittest discover tests/` for code-level checks (31/31 passing as of this update, including 13 new tests for `src/engine/native_tool_calling.py`). Run GPU integration scripts separately; the unit command does not execute them, and several of the standalone GPU scripts in `tests/` (`test_fast_path_reflex.py` and siblings) still assert behavior of the retired custom scheme and need updating before they are trustworthy again.
3. Score the native-path results against the official BFCL AST-based argument scorer instead of the loose containment check used here, for a tighter number.
4. Implement KV-cache reuse for the native path (encode the prompt once, reuse across candidate menus or multi-turn continuations) to bring the ~1.0-2.6s latency down; the official `generate()` accepts `past_key_values`, this just hasn't been wired into `ReflexEngine` yet.
5. Investigate the free-text-tool-vs-direct-response ambiguity seen in the smoke test (model answers directly instead of invoking an offered tool for genuinely tool-appropriate free-text requests) -- measure how often this happens and whether prompting (e.g. an explicit system instruction to prefer tool calls when a matching tool is offered) resolves it.
6. Build a genuine confidence/accuracy curve for the native path before attempting any calibrated exit policy (see "Calibration status" above).
7. For a paper: add a matched AR baseline scored on the same 1,051-item set and same loose-match rule, official DiffusionGemma sampling was already used (this *is* the official sampler now), full latency breakdown with KV reuse, uncertainty intervals over the 1,051-item accuracy figures, and ablations (with/without the reasoning preamble, budget sizes).

## Current conclusion

The prototype now demonstrates real, working tool-name routing (93%+, stable under randomized candidate order, on 1,051 independent examples) **and** real argument synthesis (~77% fully-correct calls, including free-text and nested-object arguments) using DiffusionGemma's own trained tool-calling format through the official generation algorithm, with no additional training. This directly reverses the prior conclusion that Tier 2/3 were fundamentally broken: they were broken by a custom scheme that asked the model to do a task it wasn't tuned for. It does **not** yet establish a calibrated fast/exit path, a KV-reuse latency optimization, official BFCL-scorer-grade argument accuracy, or resolution of the direct-response-vs-tool-call ambiguity noted above. Public release is reasonable as an explicitly experimental repository with these limits. A research paper needs the official BFCL scorer (or an equivalent rigorous one) in place of the loose match used here, a matched AR baseline on the same set, and the KV-reuse/calibration work above; but the core research question -- can a diffusion LM route and synthesize tool calls in one model, cheaper than a full AR JSON generation, without a separate classifier -- now has real, reproducible, large-sample evidence behind it.
